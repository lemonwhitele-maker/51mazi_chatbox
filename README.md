# 51mazi_chatbox

当前版本：`v1.0.0`（公开测试与验证版本）。

`51mazi_chatbox` 是基于 [51mazi](https://github.com/xiaoshengxianjun/51mazi) 官方 `v0.8.5` 继续开发的小说写作工具。它保留原项目的本地写作与创作工具，并将开发重点放在三件事上：**让 AI 围绕整本书持续协作、让建议有来源可检查、让正式修改始终由书本作者确认。**

本项目最初的目标，是把 `Codex`、`WorkBuddy` 这类 Agent 的协作体验带进一个灵活的写作编辑器：AI 不只是回答一次问题，而是能够在作者授权的范围内查阅作品、整理资料并提出可审阅的修改。如果你对项目感兴趣，但暂时不想了解技术细节，可以直接阅读[使用说明](#使用说明)。

> [!IMPORTANT]
> 当前仓库定位为**公开测试与验证版本**。它不是 51mazi 官方版本，也尚未同步上游后续版本的全部功能。界面中保留的商业推广、赞助等提示来自上游项目，以尊重软件原开发者的工作。

## 为什么做这个 Fork

长篇创作往往会遇到三个问题：

1. 正文、人物、设定、伏笔和讨论不断增长，作者可能逐渐失去对细节的把控，出现前后矛盾、遗忘伏笔或设定冲突；
2. 需要 AI 激发灵感时，创作者往往还要额外维护庞大且不断变化的资料文档，或反复上传整本书，耗时且难以持续；
3. 对于非全职写作者，一些必须完成但重复性较高的过渡、战斗或文戏容易消耗创作热情，而这些环节恰好适合由 AI 协助起草和打磨。

因此，作者需要的不只是更多的 AI 按钮，而是一个能够围绕作品持续工作的协作过程。

本项目的文件与 Harness 管理系统参考了 pi-agent 一类 Agent 框架的设计思路，并沿用 51mazi 提供的专业写作界面，对 AI 协作、上下文读取和修改确认流程进行了重构，希望让大模型真正参与日常创作，而不是停留在独立的聊天窗口中。

在当前版本中，Agent 可以根据指令读取和搜索书内内容，并为新建或修改正文、人物、设定、大纲与速记生成待确认提案，让创作形成“讨论 → AI 建议或起草 → 作者审核 → 确认保存”的协作过程。当前不提供删除正式文档的通用工具。

本分支遵循四项设计原则：

1. **一本书就是一个协作空间**
   正文、人物、设定、大纲、速记和历史讨论属于同一本书。切换模块时，不必反复复制整套背景。

2. **事实、计划与讨论彼此有别**
   已保存的正文是作品内容，大纲是计划，历史对话是讨论。系统区分这些来源，要求 AI 在整理资料时明确依据，作者仍需核对最终结论。

3. **AI 提建议，作者做决定**
   AI 对正文和资料的改动先形成可审阅提案。只有作者确认、且目标版本仍然匹配时，内容才会写入文件。

4. **作品优先留在作者手中**
   书稿、知识文档、对话记录和提案保存在本地书库中。索引可以重建，作品不依赖某一次模型会话才能继续维护。

## 从问题到正式修改

```mermaid
flowchart LR
    A[提出问题或选中正文] --> B[按需检索书内资料与历史讨论]
    B --> C[给出带来源的建议]
    C --> D[生成修改提案]
    D --> E{作者审阅}
    E -->|接受| F[检查文件版本后写入]
    E -->|拒绝| G[不修改作品]
    F --> H[条件允许时安全撤销]
```

这条流程用于减少整理资料和落实修改时的机械工作，同时保留作者对作品的最终控制。查询、讨论和审阅任务可以停留在回答阶段；只有需要改动作品时才生成修改提案。

## 本分支的主要更新

### 1. 书籍工作区与常驻 AI 对话

- 将正文、人物、设定、大纲、速记等模块定义为核心内容，并在同一书籍工作区中接入 Agent 操作。
- 提供可收起、可调整宽度的对话侧栏，切换功能时可以继续当前任务。
- 支持为人物塑造、情节规划、资料整理等任务建立多个对话。
- 对话、摘要、工具记录和修改提案由应用保存，不把长期创作过程只托付给模型会话。
- 将人物、设定和大纲等核心资料 Markdown 化，方便作者直接编辑，也方便 Agent 读取和引用。

### 2. 统一的书籍文档工具

- AI 使用 `read`、`create`、`write`、`edit` 四类内容操作，并通过 `list_files` 定位文件；同一套协议覆盖正文、人物、设定、大纲和速记。
- 书籍资料统一使用 `book/...` 虚拟路径；项目文档工具不接受磁盘盘符或内部存储路径。
- `read` 支持目录检索、短游标续读，以及一次批量读取 1–12 个文件；内置 `help/...` 文档按需说明各类资料格式。
- `create` 可生成新章节或资料文档提案，`write` 用于整章或全文替换，`edit` 用于当前选区或同一文档中的多处局部修改。
- “全文、整篇、通读、依据速记生成总纲或划分章节”等任务会检查源材料是否完整读取；未读完时不会把局部结果冒充完整整理。

#### 当前工具清单

| 工具 | 用途 | 主要参数 | 重要规则 |
| --- | --- | --- | --- |
| `list_files` | 递归列出当前书籍中的正文、人物、设定、大纲和速记 | `path`、`cursor`、`maxChars` | 默认从 `book/` 开始；历史对话需显式列出 `book/conversations/`；结果只是文件清单，不算已读取正文 |
| `read` | 读取文件、浏览目录、搜索书内内容或批量读取资料 | `path`、`paths`、`cursor`、`query`、`maxChars` | `paths` 每批 1–12 个文件；长文通过返回的短 `nextCursor` 续读；目录、搜索摘要、帮助和历史对话不能单独作为正式事实证据 |
| `create` | 新建章节、人物、设定、大纲或唯一的速记文档 | `directory`、`content`，知识文档可带 `basis/sources` | 只创建待确认提案，确认前不会生成正式文件；目录必须属于当前书籍并支持对应类型，新章节必须放入已有卷 |
| `write` | 整章重写或替换一份文档的完整内容 | `path`、`content`，知识文档可带 `basis/sources` | 必须完整读取目标的同一版本；正文存在选区时不能用 `write`，应先取消选区或改用 `edit` |
| `edit` | 替换当前正文选区，或在同一文档中执行一到多处局部修改 | `path`、`edits`，知识文档可带 `basis/sources` | 有正文选区时只提交一个完整的 `newText`；无选区时每项使用唯一匹配的 `oldText/newText`；目标范围必须已经读取 |

#### 搜索入口与旧工具去向

当前版本**没有名为 `search` 或 `search_book_knowledge` 的独立工具**，但书内搜索能力并未移除，而是合并进 `read`：对目录路径同时传入 `query` 即可搜索。例如，`read({ path: "book/", query: "失踪的钥匙" })` 会检索正文、人物、设定、大纲、速记和历史对话；也可以把路径缩小为 `book/chapters/`、`book/knowledge/characters/`、`book/knowledge/settings/`、`book/knowledge/outlines/`、`book/notes/` 或 `book/conversations/`。搜索结果是摘要和可读路径，重要内容仍需再次 `read` 原文。这里指的是**当前书籍及其历史对话的本地检索**，不是网络知识搜索；网络搜索目前尚未接入。

`create`、`write` 和 `edit` 都属于**提案工具**：工具调用成功只表示候选内容已经冻结并等待审阅，不代表正式文件已经变化。作者仍需在界面中查看差异并点击确认；拒绝提案不会修改文件，已应用提案只有在目标版本未再次变化时才能安全撤销。

工具使用的不是磁盘绝对路径，而是应用提供的虚拟路径：

```text
book/                                      # 当前绑定书籍
├─ chapters/<卷名>/<章节名>.txt            # 正文章节
├─ knowledge/characters/<文档 ID>.md       # 人物文档
├─ knowledge/settings/<文档 ID>.md         # 设定文档
├─ knowledge/outlines/<文档 ID>.md         # 大纲文档
├─ notes/quick-notes.md                    # 助手速记
└─ conversations/<对话 ID>.md              # 历史对话，只读参考

help/index.md                              # 工具总说明
help/characters.md                         # 人物文档格式
help/settings.md                           # 设定文档格式
help/outlines.md                           # 大纲文档格式
help/chapters.md                           # 正文章节规则
help/notes.md                              # 速记规则
help/references.md                         # 来源与稳定引用规则
```

知识文档的 `basis` 和 `sources` 用于区分内容依据：

- `basis=source_grounded`：根据本轮实际读取、版本仍一致的资料整理；`sources` 填对应的 `book/...` 路径。
- `basis=creative`：用户明确要求创作，不附带 `sources`，避免把构想伪装成已有事实。
- 正文和速记不使用 `basis/sources`。

典型流程是：`list_files` 定位目标 → `read` 读取并核对版本 → `create/write/edit` 生成提案 → 作者审阅并确认或拒绝 → 条件允许时撤销。

### 3. 书籍资料、来源与历史讨论检索

- 浏览并搜索正文、人物、设定、大纲、速记和历史对话；历史讨论会标记为未确认内容，不能单独证明正式事实。
- 读取正文时可返回其中命中的人物、设定候选，方便继续补读，但候选清单本身不算已读证据。
- 在回答中保留带版本的来源信息，方便作者回到原文核对，并避免资料变化后继续沿用旧证据。
- 支持人物、设定、大纲之间的稳定引用、大纲与章节关联、反向引用及大纲上下文视图。
- 知识资料根据正式内容整理时，来源必须是本轮实际读取且版本一致的资料；明确创作的内容则单独标记为创作依据。

### 4. 冻结、审阅、确认和恢复修改提案

- 正文、人物、设定、大纲和速记使用统一文档提案；创建、全文写入和局部编辑都不会直接修改正式文件。
- 局部修改默认显示着色后的改动片段和少量上下文，选区修改显示“选中原文 / 替换后文本”，也可展开查看全文对照。
- 提案会冻结原始基线和完整候选内容，并记录版本、候选哈希、来源与有效期。
- 确认写入前会检查当前回答状态、编辑器未保存草稿、提案版本、候选完整性和正式文件基线，避免覆盖较新的手工修改。
- 写入前保存撤销快照；只有正式文件仍与已应用版本一致时才允许撤销。写入中断后可根据磁盘状态恢复或标记冲突。
- 确认凭据绑定当前窗口、书籍、会话、提案版本和候选内容，过期或跨窗口操作会被拒绝。

### 5. 开放式 Markdown 知识文档

- 人物、设定和大纲统一使用独立 Markdown 文档。
- 在必要的标识、元数据和引用约定之外，允许作品保留自己的字段和内容结构。
- 大纲可通过标签、顺序、关联大纲和章节引用组织，不强制所有作品使用同一种固定层级。
- 文档索引提供诊断与重建能力；源文档仍是可直接备份和读取的本地文件。

### 6. 模型与 API 配置

- 支持 Codex App Server 兼容路径，以及由用户显式配置的 OpenAI 兼容 API 路径。
- 预设厂商增加 Cloudflare Workers AI 和 Mistral AI；每个厂商保留独立配置，“正在编辑的厂商”与“默认厂商”彼此分离。
- 每个对话可以独立选择模型和思考强度；可用强度根据 DeepSeek、GPT 等模型族的已知能力显示。
- 模型目录不可用时仍保留已保存的直连模型，并提供手动刷新；配置验证不会代替用户执行保存。
- 输出达到长度上限时不会执行可能被截断的工具请求；预算和时间允许时可以安全重试一次。
- 对话标题等轻量任务可以使用独立的功能 API 配置；不在失败时静默切换到另一个服务。

> 配置界面中出现某个厂商或模型名称，不等于该组合已经完成兼容性认证。Agent 对话所选模型还必须支持标准工具调用，请以实际测试结果为准。

### 7. 可随书库搬迁的数据与应用级配置

- 聊天模型、功能 API、DeepSeek、通义万相、Gemini、豆包及图片服务商选择统一保存在 `BookList/.51mazi/api-config.json`。
- 配置仍由整个应用共享，不需要为每一本书重复填写。
- 切换到已有配置的书库时读取其配置；目标书库没有配置时，可带入当前共享配置。
- 迁移采用备份、原子写入和读取校验，成功后才清理旧应用配置中的对应 API 项。
- 书库根目录的 `.51mazi` 不会被识别成一本书，也不会进入正文导出或书籍检索。

### 8. 单书隔离与保存可靠性

- 每个工作窗口绑定当前书籍；对话、工具、提案和事件都会核对同一书籍范围。
- 项目文档工具拒绝盘符、UNC、`..`、符号链接、junction、硬链接及越出当前书籍的路径，也不向模型直接暴露书内 `.51mazi` 目录。
- 编辑器以最后成功保存的正文快照判断未保存状态；保存期间继续输入或切换章节，不会被较晚返回的保存结果错误标记为已保存。
- 章节写入增加 UTF-8 校验、版本冲突保护、原子替换、后处理失败回滚和不记录正文内容的保存诊断。
- 字数统计按书保存在 `.51mazi/stats/word-stats.json`，使用串行更新和幂等基线，并可迁移旧的书库根级统计。
- 正文高亮从人物扩展到人物、设定及其已保存别名。

## 相较原软件开发者 `v0.8.5` 的具体功能差异

这里的“原版”指原软件开发者的 51mazi `v0.8.5`，不是已经加入聊天助手的其他 Fork 或历史预览版本。本分支将部分原版模块替换为围绕整本书协作的工作流，具体差异如下。

| 功能 | 原作者 `v0.8.5` | 本分支 | 使用上的变化 |
| --- | --- | --- | --- |
| AI 写作入口 | 编辑器中的 AI 润色、AI 续写，以及按大纲生成等独立入口 | 书籍工作区内常驻 AI 侧栏，可建立多个持续对话 | 不必为每个任务重新填写背景，可连续讨论人物、设定、情节和正文 |
| AI 上下文 | 各功能为当前生成任务临时聚合章节、大纲等资料 | AI 可列出、搜索、批量读取正文、人物、设定、大纲、速记和历史对话 | 模型按需补读资料，并在回答中保留可回到原文核对的来源 |
| 正文修改 | 润色或续写生成结果后，由对应功能复制或确认插入 | `write` 生成整章提案，`edit` 生成选区或多处局部修改提案 | 所有正文修改先审阅差异，再检查版本、未保存草稿和候选哈希后写入 |
| 新建章节 | 主要由作者在章节列表中手动新建，AI 生成内容再放入章节 | AI 可通过 `create` 生成新章节提案 | 确认前不会创建正式章节，拒绝提案不会留下空文件 |
| 人物管理 | 完整人物档案表单、人物图库，可为同一人物保存多张图片 | 独立 Markdown 人物文档、稳定引用及头像流程 | 字段和分区更开放，但原版完整档案表单与多图图库不再保留 |
| 设定管理 | 分类设定和专用表单 / AI 生成功能 | 独立 Markdown 设定文档，使用 `kind`、标签、别名和自定义分区 | 更适合自由扩展及被 AI 读取、引用，但不再使用原版分类表单 |
| 大纲管理 | 树形大纲、紧凑显示、AI 大纲草稿工作台和按大纲生成 | 独立 Markdown 大纲文档，通过顺序、标签、相关大纲和章节引用组织 | 不强制单一树形层级；原版树形编辑器和 AI 草稿工作台已移除 |
| 资料真实性 | 原版 AI 功能可读取写作上下文，但没有统一的来源状态体系 | 区分已保存正文、计划大纲、私人速记和未确认历史讨论 | 历史讨论不能单独作为正式事实；知识资料可区分“依据来源整理”和“明确创作” |
| AI 模型 | 文本生成主要围绕 DeepSeek 等原版专用接口，图片使用通义万相等服务 | Codex App Server 或用户配置的 OpenAI 兼容 Agent API；模型可按对话选择 | 可配置本地或远程兼容服务，并为不同对话选择模型及思考强度 |
| 写入安全 | 各 AI 功能分别处理确认和保存 | 统一冻结提案、窗口确认凭据、版本冲突检查、撤销快照和中断恢复 | AI 不直接覆盖正式文件；文件或编辑器状态变化时会拒绝旧提案 |
| 文件范围 | 原版各模块直接操作对应书籍数据 | 项目文档工具绑定当前窗口和书籍，使用 `book/...` 虚拟路径 | 拒绝跨书路径、盘符、UNC、`..`、符号链接、junction 和硬链接绕过 |
| 人物与设定高亮 | 正文中高亮人物名称 | 同时高亮人物、设定及已保存别名 | 编写正文时也能快速识别地点、组织、物品等设定词条 |
| 数据搬迁 | 书稿在书库中，应用 API 配置与书库分开 | 对话、提案、速记、统计保存在单书 `.51mazi`，共享 API 配置保存在 `BookList/.51mazi` | 复制完整 `BookList` 可以带走主要协作数据和软件内 API 配置 |

原版的多书籍与卷章编辑、自动保存、搜索替换、字数统计、禁词提示、封面与场景图、地图、关系图、时间线、事序图、组织架构、词典、随机名字、正文导出、书架和单书密码等能力仍然保留；本分支主要替换的是 AI 协作、人物、设定和大纲相关流程。

> [!WARNING]
> 本分支已经移除原版人物完整档案与人物图库、分类设定表单、紧凑树形大纲、AI 大纲草稿工作台及其专用代码。**原版人物、设定、树形大纲和大纲草稿不会自动迁移到新版 Markdown 文档**；首次打开旧作品时，请务必使用副本验证。

- 本地封面和 AI 封面；
- 地图设计、关系图谱、时间线、事序图和组织架构；
- 词条字典、随机名字和笔记；
- 小说正文导出；
- 书架与单本书密码等原有能力。

具体可用功能以当前源码和实际界面为准。

## 数据保存、搬迁与隐私

典型的数据结构如下：

```text
BookList/
├─ .51mazi/
│  └─ api-config.json          # 整个书库共享的 API 配置
└─ 作品名/
   ├─ mazi.json
   ├─ 正文/
   ├─ knowledge/
   │  ├─ characters/
   │  ├─ settings/
   │  └─ outlines/
   └─ .51mazi/
      ├─ harness/v1/           # 对话、记忆、工具记录、冻结提案与撤销快照
      ├─ notes/                # 助手速记
      └─ stats/                # 单书字数统计
```

在自己的设备之间搬迁时，请复制**完整 `BookList`，包括隐藏的 `.51mazi` 目录**，然后在新设备中重新选择该书库。这样可以一并带走书籍、对话协作数据和软件内 API 配置。

同时请注意：

- `api-config.json` 包含你填写的访问凭据，应被视为敏感文件；不要上传到 GitHub，也不要随公开书稿分享。
- 小说正文导出不包含 API 配置；直接分享完整书库时仍需主动排除 `.51mazi` 中的配置与迁移备份。
- 外部 Codex 的安装、登录和自身配置不在这套迁移范围内，需要单独处理。
- 尚未保存的编辑草稿不属于书库搬迁保证范围。
- 保存诊断日志位于应用数据目录，不随 `BookList` 搬迁；日志不记录正文内容，但可能包含书名、文件路径、哈希和错误信息，公开反馈前仍应检查。
- 书籍资料默认保存在本地；使用远程 AI 时，完成当前请求所需的选区、资料片段和对话上下文会发送给你选择的服务。请同时阅读相应服务商的隐私政策。

## 当前限制

- 当前是早期源码预览，不承诺生产环境稳定性。
- 知识文档目前仍偏向 Markdown 源码编辑，低门槛表单和所见即所得体验有待完善。
- 不提供旧人物、旧分类设定、旧树形大纲和旧大纲草稿的自动迁移。
- 旧工具模式生成的正文和知识提案只保留为历史记录：待处理提案需要在当前文档工具模式下重新生成，处于写入中的旧提案应人工核对正式文件。
- 更严格的完整读取、来源、版本和编辑器草稿检查，可能要求模型先补读资料或要求作者先保存草稿；这是写入保护的一部分。
- 使用符号链接、junction 或硬链接组织的书籍和资料可能因单书隔离策略而被拒绝。
- Codex 兼容模式保留只读沙箱，但其原生工具的读取范围不能保证只限当前书籍；项目文档工具的路径检查和写入确认仍然有效。需要严格限制本机文件读取范围时，可使用只暴露注册函数工具的 OpenAI 兼容 Agent API；远程服务仍会收到完成请求所需的选区、资料片段和上下文。
- 不同 API 服务对工具调用和兼容格式的支持不一致，尚未对配置列表中的所有组合逐一认证。
- 基于 `v0.8.5` 开发，不自动包含上游后续版本新增的全部功能。
- 在迁移旧作品或尝试 AI 写入前，应保留可独立恢复的书库备份。

## 使用说明

下面以日常创作任务为主介绍使用方式。文字示例中的 `【章节名】`、`【人物名】`、`【设定名】` 等均为占位符，请替换成自己作品中的内容。截图展示实际操作时的界面，书名、人物和模型名称仅用于说明，使用时无须与截图一致。

### 快速上手

1. 打开一本书，进入书籍工作区并展开 AI 对话侧栏。
2. 新建对话，选择已经配置好的模型和思考强度。
3. 如果准备修改当前章节，先保存编辑器中尚未保存的内容。
4. 直接用自然语言说明目标、范围和限制。通常不需要手写 `read`、`edit` 等工具参数，Agent 会按需选择工具。
5. Agent 可能先列出或搜索资料，再读取相关原文。较长任务会产生多次读取，这是正常流程。
6. 如果回答包含修改提案，请在差异预览中检查内容，再选择确认或拒绝。确认前正式文件不会变化。

![书籍工作区与常驻 AI 对话侧栏](assets/readme/writing-workspace.png)

左侧切换章节与资料模块，右侧选择对话、模型和思考强度，并向助手提出任务。

### 基础配置

#### AI 设置

在“AI 设置”中选择接入通道。界面提供“Agent API 直连”和“Codex 反代”两种入口，按已配置好的服务选择即可；两种通道的配置与可用模型分别取决于对应服务。

DeepSeek、Gemini、Grok 和 Mistral已经过多轮测试可以稳定使用。“Codex 反代”是指打开codex(chat-gpt桌面端)之后，直接用openai的额度来驱动agent，欢迎额度用不完的用户测试astra写文的效果。

| 配置区域 | 用途 | 配置要点 |
| --- | --- | --- |
| Agent API | 承担主要对话、资料检索、写作与修改提案 | 所选模型需要支持工具调用；填写对应厂商的接口地址、密钥和模型名称 |
| 功能 API | 为新对话自动生成标题等轻量任务 | 可单独使用成本较低的模型；未配置或不可用时，使用本地规则生成标题 |
| 视觉 / 图片相关配置 | 上游保留的图片服务配置 | 不属于本次写作助手的验证重点，尚未完成回归测试；纯文字协作不需要配置 |

配置时注意区分“默认厂商”和“编辑厂商”：切换编辑对象不会自动更改默认厂商。完成填写后可先验证连接，再点击“保存”；验证成功不等于配置已经保存。进入书籍后，还可以为每个对话单独选择模型和思考强度。

![AI 设置中的 Agent API 和功能 API 配置](assets/readme/ai-settings.png)

### 常用案例

#### 1. 查询书内事实或回顾已有内容

适合确认人物经历、设定规则、章节事件和以前讨论过的方案。只想得到答案、不希望修改文件时，应明确说明“只分析，不生成修改提案”。

可以这样说：

> 请搜索当前书中与【关键词】有关的正文、人物和设定资料，总结已经明确写入作品的事实，并列出来源。只分析，不修改任何文件。

> 我记得以前讨论过【主题】，请同时检索历史对话，区分哪些只是讨论、哪些已经写入正文或正式资料。

使用细节：

- 搜索结果只是定位线索。Agent 应继续读取命中的原文后再下结论。
- 历史对话属于未确认讨论，不能单独证明作品事实。
- 范围明确时可直接指定“只查正文”“只查人物资料”或“只查某一卷”，减少无关结果。

![助手查询书内人物资料并在回答下方列出来源](assets/readme/book-search-answer.png)

示例回答区分了规划中的人物信息与正文已确认的事实，并提供了来源入口。

#### 2. 润色、改写或扩写选中的正文

在编辑器中选中需要处理的段落，再说明希望保留什么、改变什么。选区任务适合小范围润色，修改提案只替换所选内容。

可以这样说：

> 润色当前选中的文字，保留原意和叙事视角，减少重复表达，使节奏更自然。请生成修改提案，不要改动选区之外的内容。

> 扩写当前选中的段落，重点补充【动作／环境／情绪】，总长度控制在原文的【倍数或字数范围】以内，不新增会影响后续情节的事实。

> 在保留当前选区原文的基础上向后续写【大致字数】，并保持现有语气。不要替角色做出尚未确定的关键决定。

使用细节：

- “润色、改写、扩写”会用新文本替换整个选区；“在选区后续写”应明确要求保留原文并追加内容。
- 发送请求后不要继续改变选区或目标章节，否则旧提案可能因版本不一致而失效。
- 正式接受前应重点检查人称、时态、角色口吻以及是否意外新增设定。

![选中正文后生成润色提案，对照选中原文与替换后文本](assets/readme/selection-edit-proposal.png)

图中提案仍处于“待确认”状态，可以先检查修改内容，再点击“确认写入”或取消。

没有选区时，也可以要求助手处理同一章节的多处问题，例如补全对话中的说话人。此时提案按改动位置展示原文与建议片段：

![同一章节中多处对话归属调整的局部修改提案](assets/readme/multi-edit-proposal.png)

#### 3. 审阅或重写整个章节

适合检查章节节奏、信息重复、视角跳变和情节衔接。建议先让 Agent 给出诊断，再决定是否生成整章提案。

可以这样说：

> 完整阅读【章节名】，从节奏、人物动机、信息释放和前后衔接四个方面给出审阅意见。先只分析，不修改正文。

> 根据刚才的审阅结果重写【章节名】，保留【必须保留的情节或台词】，重点改善【目标】。请生成整章修改提案。

使用细节：

- 整章任务开始前应保存正文并取消选区，否则系统会要求改用选区编辑。
- Agent 必须完整读完目标章节，不能用搜索摘要或局部片段代替全文。
- 整章提案影响范围较大，确认时建议展开全文对照；若只需改几处，应要求“仅修改明确指出的位置”。

<!-- 待补截图：整章审阅与全文替换提案。 -->

#### 4. 根据现有内容整理人物、设定或大纲

适合把已经写入正文的事实整理成知识文档，或补充现有资料。此类任务应区分“依据作品整理”和“自由创作”。

依据现有内容整理：

> 阅读【章节范围】，整理其中已经明确出现的【人物／地点／组织／规则】信息。先列出依据，再为对应资料生成新建或更新提案；不要把推测写成事实。

自由创作资料：

> 为【人物／设定／大纲主题】设计一份新资料，满足以下限制：【限制条件】。这是创作任务，不要声称内容已经出现在正文中。

使用细节：

- 依据正文整理时，系统会记录本轮实际读取的来源；只被搜索命中但没有读过的文件不能作为正式依据。
- 自由创作的资料会标记为创作内容，不附会成已有事实。
- 更新已有资料前，Agent 仍需先读取该文档，避免覆盖自定义字段或作者手写分区。

<!-- 待补截图：依据来源整理人物或设定资料的提案。 -->

#### 5. 根据大纲起草新章节

适合在卷已经存在的前提下，根据大纲和相邻章节生成新章节提案。

可以这样说：

> 阅读【大纲名】以及【前一章节】的结尾，先总结新章节必须承接的事实和限制，再在【卷名】中新建一章。暂定标题为【标题要求】，篇幅约【字数范围】，不要提前解决【后续悬念】。

使用细节：

- 新章节必须放入已有卷；如果目标卷不存在，应先由作者在界面中建立或调整结构。
- 最好明确视角人物、章节目标、必须发生和禁止发生的事件。
- `create` 生成的是待确认提案；拒绝后不会留下空章节。

如果已经手动建立了空章节，也可以要求助手直接起草该章内容。下面展示的是向已有空章节写入草稿后的状态，不是新建章节操作：

![章节开头草稿确认写入后显示在编辑器中](assets/readme/chapter-draft-applied.png)

提案卡片显示“已写入”，并提供“撤销”入口；撤销仍需满足文件版本未再次变化等条件。

#### 6. 检查跨章节一致性和伏笔

适合核对人物状态、时间顺序、道具流转、设定规则和伏笔回收。范围越大，读取时间和上下文消耗越高，建议先限定卷、章节或问题类型。

可以这样说：

> 阅读【章节范围】，检查【人物状态／时间顺序／道具去向／设定规则】是否前后一致。把“原文明确冲突”“可能存在歧义”和“尚未交代”分开列出，并附上对应来源。先不要修改正文。

> 搜索与【伏笔关键词】有关的章节和资料，整理首次出现、后续强化、可能回收和仍未处理的位置。不要仅凭历史讨论认定已经埋设或回收。

使用细节：

- 百章节级任务建议按卷或主题分批检查，再汇总每批已经确认的结果。
- “没有搜到”不等于“一定不存在”；重要结论应以完整读取的章节范围为准。
- 发现问题后，建议逐项生成小范围修改提案，避免一次改动过多章节。

![对照不同章节与人物资料，检查人物表现是否一致](assets/readme/chapter-consistency-review.png)

示例回答将明确冲突与语气、动机上的变化分开讨论，供作者判断是否需要补充过渡。

#### 7. 记录灵感与回顾历史讨论

速记适合暂存灵感、待办和需要以后确认的内容；历史对话适合找回曾讨论但尚未正式采用的方案。

可以这样说：

> 把下面的想法整理成简短速记，保留不确定语气，并放到合适的标题下：【想法】。

> 搜索历史对话中关于【主题】的讨论，按“已采用、明确否决、仍待决定”分类。无法从正文或正式资料验证的内容不要标记为已采用。

使用细节：

- 速记不是正式设定；需要落实时，应再整理成人物、设定、大纲或正文提案。
- 归档速记会把完整内容块移动到同一文档的 `## 归档` 分区，不会创建额外速记文件。
- 删除正式文档目前没有通用工具；知识资料不再使用时，可将状态改为 `deprecated`，但文件仍会保留。

![根据创作想法同时生成速记更新与章节大纲新建提案](assets/readme/notes-and-outline-proposals.png)

一次请求可以产生多个提案。图中的速记和大纲分别等待确认，需要逐项审阅；它们尚未写入正式文件。

### 更容易获得理想结果的提问方式

一条实用指令通常包含四部分：

1. **范围**：当前选区、某章、某卷、某类资料或指定章节范围；
2. **目标**：分析、搜索、续写、润色、新建资料或生成修改提案；
3. **约束**：必须保留、不得新增、篇幅、视角、语气和禁止触碰的情节；
4. **输出方式**：只回答、先分析后修改，或直接生成待确认提案。

例如可以使用这个通用模板：

> 请处理【范围】，目标是【目标】。必须保留【内容】，不要【限制】。先【需要的读取或分析】，然后【只给建议／生成修改提案】。

如果结果偏离预期，优先补充范围和限制，不必尝试手动指定工具。需要查看 Agent 实际做了什么时，可以展开工具记录，确认它读取了哪些资料、是否完整读完，以及最终生成了哪一类提案。
